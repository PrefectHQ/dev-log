Let's start with the bug, because it's a good one and it deserves to be understood before we watch what happened to it. [Issue #22184](https://github.com/PrefectHQ/prefect/issues/22184): the ProcessWorker checks whether `working_dir` contains a `pyproject.toml` *before* it runs the deployment's pull steps. So a `git_clone` deployment — the single most common way anyone deploys anything — looks at an empty directory, finds no project, shrugs, and runs the flow in the worker's own venv. The auto-`uv run` feature shipped in 3.7 was, for process workers, decorative. The fix is one sentence long: check *after* the clone.

[PR #22857](https://github.com/PrefectHQ/prefect/pull/22857) is titled "Fix ProcessWorker auto-uv after pull steps." It is +2,237 / -561 across 25 files.

Here is what the one-sentence fix required. A new `_workspace_supervisor.py` (204 lines), which is a child process whose job is to run the pull steps and then launch the engine. A new `_workspace_runtime_bootstrap.py` (200 lines), which is a *second* script the supervisor launches so the engine can be launched from *inside* the uv environment. A new `_workspace_runtime.py`, which defines the JSON manifest format the supervisor writes to disk so the parent can later find out what the supervisor decided. A new `_workspace_hook_runner.py`, which spawns a *third* kind of subprocess to run `on_cancellation` hooks, and communicates with it by writing the `FlowRun` and `State` to two more JSON files. And, deep in `_process_manager.py`, [three `ctypes.Structure` subclasses](https://github.com/PrefectHQ/prefect/blob/main/src/prefect/runner/_process_manager.py) hand-transcribing `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` from the Win32 headers so the whole tree can be killed on Windows. Read that list again. A bug about the order of two function calls was closed with a process supervision hierarchy, a serialization format, and a hand-rolled Windows job object API. This is a man who was asked to move a lamp and came back with a floor plan.

To be fair — and I say this through gritted teeth — the reason it grew is real. Once you move "decide the command" to after the pull steps, the pull steps are running before the parent has a process handle to cancel, so you need *something* that owns the process group from the start. That's a legitimate constraint. But the response to "I need one long-lived child process" was to design an entire runtime with its own bootstrap protocol, and the tell is `_run_engine` in the bootstrap script. It does `sys.modules.pop("prefect.engine")`, then `runpy.run_module("prefect.engine", run_name="__main__")`, then puts the module *back*. Why? Because the uv environment might have an older Prefect pinned in it, and older Prefect doesn't expose `flow_engine._main`. So this PR ships, inside the current version of Prefect, a compatibility shim for running previous versions of Prefect. The package has become its own legacy integration.

The review is where the process really shines. There are 43 comments on this PR, 26 of them findings, and every single one is from `chatgpt-codex-connector[bot]`. No human reviewed this. The branch is literally named `codex/process-worker-pulled-auto-uv`. Eleven consecutive rounds of Alex pushing a commit, the bot finding two to four new P1s, Alex pushing a commit titled something like "Address workspace supervisor review feedback," the bot finding two to four more. This went on for eight days. Highlights from the bot's greatest hits: `os.fchmod` doesn't exist on Windows before 3.13, so the very first manifest write would `AttributeError` and every ProcessWorker run on Windows would fail — caught in round two. The supervisor returned the engine's exit code through `SystemExit`, which converts `-15` to `241` modulo 256, so a SIGTERM'd engine would be reported as an exotic userland failure — caught in round two. And my personal favorite: the PR updated `AGENTS.md` to instruct future contributors to pass `starter.resolve_flow` into the executor, in the same commit that *deleted* `resolve_flow`. The documentation was outdated before it was merged. The bot had to file a P2 against the instructions written for the bot.

Now the commit log, which is a genre unto itself. The last four substantive commits are *Preserve legacy workspace engine execution*, *Restore workspace bootstrap process state*, *Preserve runner ownership during workspace preparation*, and *Preserve workspace attribution metadata*. Add the bot's findings — *Preserve signal exit codes, Preserve the prepared environment, Preserve custom command runtimes, Preserve hooks when workspace preparation ends early, Preserve the worker API settings after pull steps* — and you have over a dozen things that needed preserving. You do not need to preserve this many things when you're fixing a bug. You need to preserve this many things when you've knocked down a load-bearing wall and are now walking around the house with a clipboard writing down everything that fell. The final one produced `_RUNNER_OWNED_ENV_KEYS`: a hand-maintained list of thirteen environment variables that the pull steps are allowed to clobber but which the supervisor then quietly puts back. A denylist of your own program's side effects, on your own program.

And yet. Buried in the supervisor is the one genuinely elegant move in the whole PR: on POSIX, [`_launch_engine`](https://github.com/PrefectHQ/prefect/blob/main/src/prefect/runner/_workspace_supervisor.py) doesn't spawn the engine at all. It calls `os.execvpe`. The supervisor process *becomes* the engine — same PID, same process group, so the `infrastructure_pid` the parent recorded during the pull steps stays valid and every signal path just works. No wait loop, no signal forwarding, no exit code laundering. It's clean, it's correct, and it's a syscall from 1979. The single best idea in 2,237 lines of new Python is one Ken Thompson had before the author was born, and it took eleven rounds with a robot to arrive at it. The Windows branch, meanwhile, still spawns, still waits, and still forwards signals — so the elegance is aspirational on half the platforms.

**Final Verdict:**
**Process Architect** — asked to swap two lines, built an init system, got code-reviewed by a chatbot for eight days, and shipped the fix via a 47-year-old syscall.
