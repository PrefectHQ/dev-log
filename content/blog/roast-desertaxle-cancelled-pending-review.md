[PR #22238](https://github.com/PrefectHQ/prefect/pull/22238) has an honest job. When a flow run gets stuck in `CANCELLING` — the user hit cancel, but the infrastructure never got the memo — something needs to notice, mark the run `Cancelled` for real, and tell a worker to go tear down the leftover pod. desertaxle's producer does exactly that: a keyed Docket timeout task wakes up after 300 seconds, writes a `Cancelled` state, and enqueues `cancelling_timeout_teardown.v1`. The PR description calls that timeout state "the cleanup authority." The authority. Load-bearing noun. Remember it.

Because the very first thing the [Codex review bot](https://github.com/PrefectHQ/prefect/pull/22238#discussion_r3414304228) did was file a P1 explaining how the authority gets overruled. The timeout task commits `Cancelled` through `CoreFlowPolicy`, and `CoreFlowPolicy` cheerfully permits `CANCELLED → COMPLETED` and `CANCELLED → FAILED`. Meanwhile the original flow process is still alive — that's the entire reason we're here — and if it reports a final state in the window before teardown lands, your user-cancelled run quietly finishes as **Completed**. You clicked cancel. The reaper marked it dead. The corpse got up and reported success. This is a 1,281-line PR whose thesis is "I am the authority on cancellation," shipping a race where cancellation is the one thing that doesn't stick.

That was one comment. The bot kept reading. It found the "backstop" service — `ensure_cancelling_timeout_checks`, the safety net that seeds timeout checks for runs already stuck in `CANCELLING` — and pointed out it pages through exactly the earliest 200 rows every single loop, on the same per-run keys, forever. So if you've got 201 stranded runs, run number 201 waits for the first 200 to leave `CANCELLING` before it's even *considered*. It's a backstop with a hole in it, positioned precisely where the ball was already rolling.

And then, my favorite, because it's the one that isn't even a hard bug — it's just a man who didn't read the house rules. desertaxle gave his brand-new `cancelling_timeout_seconds` setting a `validation_alias` pointing at `PREFECT_API_SERVICES_CANCELLATION_CLEANUP_CANCELLING_TIMEOUT_SECONDS`. That alias format exists for *backward compatibility with legacy env vars*. This setting was born that afternoon. It has no legacy. He manufactured a deprecated name for a variable that had existed for zero seconds. The bot's response was to [quote `settings/AGENTS.md` back at him](https://github.com/PrefectHQ/prefect/pull/22238#discussion_r3414304236) — the repo's own written instructions, the ones titled literally "What NOT to do for new settings." When the robot has to cite your team's documentation to you, you are not being reviewed, you are being tutored.

By the time the dust settled, the bot had also flagged a 500-on-accepted-cancellation, a restart-with-`memory://`-Docket path that leaves infrastructure alive indefinitely, and a CodeQL log-injection hit. Five substantive findings and a security scan, and the commit log reads like a confession transcript — "Use Docket identity," "Clarify conditional scheduling," "Make cleanup enqueue recoverable," each one a polite euphemism for *fix the thing the machine found.* The lone human review arrived at the very end, from zzstoatzz, in full: "looks good to me!" It did, by then. The robot had already done the hard part.

The naming deserves its own moment. When the bot got done, the scheduling helper had been renamed from `schedule_cancelling_timeout_check_for_state` to `maybe_schedule_cancelling_timeout_check_for_state`. That `maybe_` is the most honest identifier in the file — a function that has been reviewed into a state of visible anxiety about whether it should do its own job. It sits next to `CANCELLING_TIMEOUT_CANCELLED_MESSAGE` and a boolean called `timeout_cancelled_state_already_committed`, in a module that logs `"Flow run %s ... skipping ..."` six nearly identical ways, as if narrating each thing it declined to do will make up for the one thing it did wrong.

I'll give him this, meanly: the idempotency is genuinely careful. He built a `uuid5` message id scoped to the exact flow run *and* the exact cancelled state id, so a later cancellation with a new PID produces distinct cleanup work and nothing double-fires. It's meticulous, load-bearing, correct engineering. He put a deadbolt, a chain, and a fingerprint scanner on the front door of the vault — and left the back wall open so the money could walk out and file itself as a deposit.

**Final Verdict:**
**Codex's Intern** — writes the PR, lets the robot write the review, and ships when the bot runs out of comments.
